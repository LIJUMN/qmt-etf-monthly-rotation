| # | 知识点 |

## 三、"跑不通"的根因定位与验证方法

### 3.1 五类根因（按本机实际出现频率排序）

| 类 | 根因 | 典型症状 | 本机是否发生过 | 验证方法 |
|---|---|---|---|---|
| **B 类** | **环境参数没设对** | 回测能跑完、没报错、有成交，但净值远低于预期；日志刷 `大于当前周期允许回测交易的最大量` | ✅ 发生多次（最大成交比例 0.05%） | **看日志**：出现 `最大成交比例:0.0005` 或 `小于需卖量...跳过` 即确诊 |
| **A 类** | **API 契约理解错** | 零输出零成交；或价格差 2–4 倍；或全程只买不卖 | ✅ 发生多次（`isinstance` 守卫、`end_time` 缺失、`dividend_type` 缺失） | **三条铁证**：① 策略打印价 vs 行情软件同日价差 1% 以内？② 差的品种是不是都做过折算？③ 交易明细里有没有相邻两月"买 31 万→卖 21 万"？ |
| **C 类** | **数据本身脏** | 净值腰斩、单日出现 -50% 的假断崖 | ✅ 512480/512760/513100 等已确认 | **扫断崖**：计算 `r = c[i]/c[i-1]`，`r<0.8 或 r>1.3` 即折算日（ETF 有 10%/20% 涨跌停，正常绝不可能单日 25%+） |
| **D 类** | **平台能力边界** | 多标的轮动跑着跑着就失败、账目全乱 | ✅ 31 个版本实测失败 | **对拍**：离线用同逻辑算一遍。若离线为正、QMT 为负 → 是平台边界不是代码错 |
| **E 类** | **代码自身逻辑错** | 状态丢失、0 股废单、异常中断整根 K 线 | ✅ `isinstance` 守卫、0 股下单都发生过 | **看 CHECK 日志**：数据长度在涨吗？持仓数在变吗？ |

### 3.2 判定流程（照着走，5 分钟定位）

```
第1步：日志有 "start back test mode" 吗？
   ├─ 没有 → 你点的是「运行」不是「回测」（D 类认知问题）
   └─ 有 → 第2步

第2步：日志有 "READY/START" 吗？
   ├─ 没有 → 卡在"启动本地Python"未勾 / 未编译 / 新建时选了 VBA 模型（B 类）
   └─ 有 → 第3步

第3步：日志有 CHECK 行的数据长度在递增吗？
   ├─ 不变或恒定 → end_time 没传，数据冻结在历史末尾（A 类）
   └─ 在涨 → 第4步

第4步：日志有 "大于当前周期允许回测交易的最大量" 吗？
   ├─ 有 → 最大成交比例没改成 100%（B 类，改参数即可）
   └─ 没有 → 第5步

第5步：策略打印价 vs 行情软件同日价，差多少？
   ├─ 差 2–4 倍且集中在折算过的品种 → dividend_type 口径错（A 类）
   └─ 差 1% 以内 → 第6步

第6步：卖出信号出现了吗？成交明细里有卖出记录吗？
   ├─ 有信号无卖出成交 → 查持仓不足告警（B 类）或状态丢失（E 类）
   └─ 都有 → 问题在撮合细节，回测≠实盘属正常，进入风控与实盘流程
```

### 3.3 一个必须建立的认知

**"代码跑不通"里，大部分不是代码错，是环境理解偏差。** 你这 31 个轮动版本失败的真实原因不是 Python 写得不好——是**引擎的三个静默约束**（成交比例截断、复权口径差、除权数据缺失）在同时作用。

这三条的共同特征是：**不报错、不警告、只是结果不对**。所以真正的排查能力不是读代码，是**读日志 + 对账**。

## 四、可执行的改进方案

### 4.1 代码规范（10 条，直接可贴进 `AI接手须知.md`）

1. 首行 `#encoding:gbk`，文件保持纯 ASCII（中文注释和 print 会被吞）
2. 状态一律模块级 `class G(): pass` + `g = G()`，**永不存 ContextInfo**
3. **`handlebar` 整体包 try/except**，异常 `print('ERR', str(e)[:120])`
4. **回测取价用 `get_market_data`**，显式传 `stock_code` + `end_time` + `count` + `dividend_type`
5. 结果用 `df['close'].values` 取，**绝不加 `isinstance` 守卫**
6. 下单前判数量 ≥ 100，ETF 按 100 股整手
7. **每根 K 线（或每 3 根）print 一行 CHECK**：日期、数据长度、最新价、真实持仓、账本现金
8. 集中常量放文件顶部（`POOL/LOOKBACK/MAF/CASH_USE`），便于改与对照
9. 策略代码里不出现任何文件读写、网络请求、`time.sleep`
10. 每个策略配一个"预期成绩单"（离线预测值），跑完必对账

### 4.2 模块划分（六层，建议单标的策略按此重构）

```
① 配置层   常量区：标的、参数、账号占位符、时间窗、风控阈值
② 取数层   get_close(code, day, n)  →  统一处理 end_time/count/dividend_type/折算修复
③ 指标层   ema / macd / ma  →  纯函数，输入数组输出数组，不碰 ContextInfo
④ 信号层   on_bar(a, state) →  只返回 'BUY' / 'SELL' / None，不下单
⑤ 执行层   do_buy / do_sell  →  唯一接触 passorder 的地方，负责整手、限价、守卫
⑥ 护栏层   风控检查 → 下单前置：单日亏损、连续亏损、持仓集中度、最大回撤
```

**分层的好处**：信号层可以完全脱离 QMT 离线单测（这正是你 12 个研究脚本在做的事），执行层只做"把信号变成订单"，出 bug 时能立刻定位是哪一层。

### 4.4 风控层（当前完全缺失，建议补 6 项）

| 风控项 | 建议阈值 | 为什么 |
|---|---|---|
| 单日亏损熔断 | 当日浮亏 > 3% 当天不再开仓 | 防止情绪化加仓/追损 |
| 连续亏损暂停 | 连亏 3 次 → 停 5 个交易日 | 策略失效的早期信号 |
| 最大回撤降仓 | 从峰值回撤 > 20% → 仓位减半；> 30% → 停机 | 回测显示单标的回撤可达 51% |
| 持仓集中度 | 单只标的上限 100%（现状），但**禁止加仓** | 满仓单只 ETF 是最大风险源 |
| 流动性闸门 | 当日成交额 < 5000 万不下单 | 防止买得进卖不出 |
| 异常熔断 | 连续 3 日无 `SIGNAL` 日志 → 告警 | 静默失效是最隐蔽的风险 |

> **注意风控与回测的冲突**：回测已证明"加任何额外止损都在掉收益"。所以**风控层不要放进回测做参数优化**，而是作为**独立的实盘执行闸门**单独验证——这需要用 `g.risk_state` 把风控状态与信号状态解耦。
